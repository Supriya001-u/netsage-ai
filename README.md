# NetSage AI

**AI-assisted troubleshooting for Cisco-style / Packet Tracer lab networks —
with a deterministic rule checker, evidence-grounded AI diagnosis, and
mandatory human review.**

## Problem Statement

Junior network engineers troubleshooting Cisco/Packet Tracer labs (VLAN,
gateway, DHCP, DNS, routing, ACL, NAT, wireless faults) often have to
manually correlate symptoms with `show`-command output and prior
experience. NetSage AI assists with this by:

1. Accepting a symptom, topology note, and `show`-command evidence.
2. Running a deterministic rule checker (no AI) for structural
   misconfigurations.
3. Producing an AI diagnosis that cites the actual evidence, states a
   confidence score, names the OSI layer, and recommends a next command and
   fix steps.
4. **Never** auto-applying anything — every diagnosis requires a human to
   Accept, Edit, or Reject it.

## Objectives

- Build a working, demonstrable AI + rule-based troubleshooting pipeline
  covering VLAN, gateway, DHCP, DNS, routing, ACL, NAT, and wireless faults.
- Keep a human reviewer in the loop for every single diagnosis.
- Provide a transparent, evidence-grounded AI diagnosis process, including
  honest confidence scores and citations.
- Document and demonstrate real cases where the AI is wrong and a human
  corrects it (Responsible AI).
- Provide a dashboard for issue analysis, severity, and AI-human agreement.

## Features

- 35 realistic, internally-consistent troubleshooting cases across 8 fault
  categories with real Cisco `show`-command-style evidence.
- A 12-check deterministic Python rule checker requiring no AI/API access.
- An AI diagnoser with a **mock mode** (default, works offline) and an
  isolated **live LLM mode** (Anthropic API) behind a single interface.
- A structured JSON diagnosis schema with mandatory evidence citation and
  confidence calibration.
- A full Accept/Edit/Reject human review workflow with persisted logs.
- A Responsible AI log documenting 5 real AI mistakes and their corrections.
- A Streamlit dashboard: overview metrics, issue analysis, severity
  breakdown, Responsible AI panel, and per-case detail view.
- A CLI pipeline (`main.py`) supporting single-case, guided demo, and
  full-dataset batch modes.
- A test suite covering both the rule checker and dataset integrity.

## Architecture

See [`docs/architecture.md`](docs/architecture.md) for the full pipeline
diagram and module responsibilities. In short:

```
INPUT -> case selection -> rule-based validation -> AI diagnosis ->
evidence comparison -> human review (Accept/Edit/Reject) ->
final diagnosis -> dashboard/logging
```

## Installation

```bash
cd netsage-ai
python3 -m venv venv          # optional but recommended
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

If you only ever plan to use mock mode (no API key), you can skip
installing the `anthropic` package by commenting it out of
`requirements.txt` — nothing else in the app imports it.

## Running the Application

**CLI — list all cases:**
```bash
python3 src/main.py --list
```

**CLI — interactively run the full pipeline for one case (Accept/Edit/Reject prompts):**
```bash
python3 src/main.py --case CASE-025
```

**CLI — guided demo case (see `docs/demo_script.md`):**
```bash
python3 src/main.py --demo
```

**CLI — non-interactive batch run over all 35 cases (writes `outputs/sample_diagnoses.json`):**
```bash
python3 src/main.py --batch
```

**Dashboard:**
```bash
streamlit run src/dashboard.py
```
Then open the local URL Streamlit prints (typically `http://localhost:8501`).

## LLM / API Configuration

All LLM integration is isolated inside `src/ai_diagnoser.py` behind one
function: `diagnose(case, rule_findings)`.

1. Copy `.env.example` to `.env`.
2. Leave `MOCK_MODE=true` to run with zero configuration (default), or set
   `MOCK_MODE=false` and add your `ANTHROPIC_API_KEY` to call the real
   Anthropic API (model: `claude-sonnet-4-6`).
3. Load the `.env` file however you prefer (e.g. `export $(cat .env | xargs)`
   on Linux/macOS, or a package like `python-dotenv` if you'd like to wire
   that in) — the app reads `os.environ`, it does not parse `.env` itself,
   to avoid adding an extra dependency for the mock-mode default path.

**API keys are never hard-coded anywhere in this repository.**

**Graceful failure handling (live mode):** if the API key is missing, the
Anthropic API errors out, the response can't be parsed as JSON, or the
network call times out/fails, `diagnose()` catches this and returns a
clearly-labelled fallback diagnosis (`_source: "error_fallback"`,
`confidence: 0`, `needs_human_review: true`) instead of crashing the CLI
or dashboard.

## Mock Mode

With `MOCK_MODE=true` (the default), `ai_diagnoser.py` returns deterministic
diagnoses built from the case's own data — no network access or API key
required. Five specific cases (`CASE-004`, `CASE-008`, `CASE-012`,
`CASE-025`, `CASE-028`) intentionally return a plausible-but-wrong
diagnosis so the full Accept/Edit/Reject review workflow, and the
Responsible AI log, can be demonstrated end-to-end offline. See
`ai_diagnoser.KNOWN_AI_MISTAKES` and `docs/responsible_ai.md`.

## Dataset Explanation

`data/sample_cases.json` (canonical) and `data/cases.csv` (same data,
flattened) contain 35 cases spanning Low/Medium/High/Critical severity,
with this exact category distribution (verified programmatically, not
estimated):

| Category | Count | Case IDs |
|---|---|---|
| VLAN | 5 | CASE-001–005 |
| Gateway | 4 | CASE-007–010 |
| DHCP | 5 | CASE-011–015 |
| DNS | 4 | CASE-016–019 |
| Routing | 5 | CASE-020–024 |
| ACL | 4 | CASE-025–028 |
| NAT | 4 | CASE-006, CASE-029–031 |
| Wireless | 4 | CASE-032–035 |

Each case has: `case_id`, `symptom`, `topology_note`, `show_outputs` (a
dict of `{command: output}`), `expected_fault`, `osi_layer`, `concept`,
`severity`, and `category` (one of the 8 values above — added during the
audit pass so dashboard/test category counts are exact and never
double-count a case). Every case's evidence is internally consistent —
e.g. a case claiming an interface is administratively down always shows
exactly that string in its `show ip interface brief` evidence. The dataset
was built programmatically by `tools_generate_data.py` (not part of the
runtime app) so its construction is transparent and reproducible.

## Human-Review Workflow

Every AI diagnosis is passed to `human_review.save_review()`, which:
- requires a decision of `ACCEPT`, `EDIT`, or `REJECT`;
- requires a `corrected_diagnosis` and reason for `EDIT`/`REJECT` (raises
  an error otherwise);
- stores the result — including the AI's full original response
  (`ai_diagnosis_full`), its root cause/confidence, and the human's final
  diagnosis and timestamp — to `outputs/review_log.json`.

The CLI's interactive Accept/Edit/Reject prompt (`main.py`) validates the
decision and required fields, re-prompting on invalid input rather than
crashing, and aborts cleanly (without saving a partial decision) if input
is interrupted or unavailable.

See `prompts/reviewer_prompt.md` for the guidance shown to reviewers.

## Responsible AI

See [`docs/responsible_ai.md`](docs/responsible_ai.md) and
`data/responsible_ai_log.csv` (columns: `case_id`, `ai_diagnosis`,
`ai_confidence`, `correct_diagnosis`, `reviewer_decision`, `correction`,
`reason`, `lesson_learned`) for the 5 documented cases where the AI's
initial diagnosis was wrong and a human corrected it, plus the principles
this project follows (mandatory review, evidence grounding, calibrated
confidence, no autonomous action). Each of the 5 cases demonstrates a
different failure mode: routing-vs-ACL (CASE-025), DHCP outage-vs-pool-
exhaustion (CASE-012), VLAN-vs-trunk (CASE-004), DNS-vs-gateway (CASE-008),
and NAT-vs-blocking-ACL (CASE-028).

## Limitations

- The rule checker's regex parsing is tuned to this dataset's evidence
  format, not a full production-grade Cisco CLI parser.
- Mock-mode diagnoses demonstrate the workflow; they are not a claim that
  any specific live LLM will reach identical conclusions on unseen data.
- Roughly half of the 35 cases do not trigger a deterministic rule-checker
  finding by design — those require the AI's evidence reasoning, which is
  the intended division of labour (see `docs/architecture.md` §2).
- This is a lab/teaching-scale dataset (Packet Tracer scale), not a
  production network monitoring tool.

## Future Improvements

- Replace the regex-based rule checker with a proper CLI/NETCONF parser
  (e.g. Genie/pyATS) for real hardware or Packet Tracer XML export.
- Add authentication and multi-reviewer support with review history/diffs.
- Expand the Responsible AI log automatically from live-mode review
  sessions rather than only the curated 5-case set.
- Add a feedback loop that fine-tunes prompt few-shot examples based on
  frequently-corrected diagnosis categories.

## Audit Findings & Fixes (this pass)

A line-by-line audit against the original brief found and fixed 6 real
implementation issues (not just documentation gaps) — see
`docs/architecture.md` §6 for full detail:

1. Dashboard category counts were inflated by fuzzy keyword matching
   (fixed with an explicit `category` field on every case).
2. Dataset was VLAN-heavy (6) and NAT-light (3); rebalanced to 5/4 by
   rewriting `CASE-006` into a genuine, distinct NAT case.
3. `check_acl_blocking` produced a false WARN on standard/NAT-source ACLs.
4. `check_gateway_mismatch` had a latent false-positive risk (it would
   have flagged every gateway as mismatched had the evidence format been
   slightly different).
5. Live-mode AI failures (missing key, API error, malformed JSON, network
   error) were unhandled exceptions; now caught and returned as a graceful
   fallback diagnosis.
6. The CLI's interactive review prompt crashed on invalid input; now
   validates and re-prompts.

All fixes are covered by new or updated tests (test suite grew from 20 to
42), and the full test suite, CLI (`--list`, `--case`, `--demo`, `--batch`,
invalid-input and invalid-case-id paths), and dashboard (via
`streamlit.testing.v1.AppTest`) were re-verified after every change in
this pass — see the audit summary in the delivery message for exact
command output.

## Assumptions Made

1. Where the brief said "improve the structure if there is a better
   design," the proposed structure was kept as-is since it was already
   clean and matched the requirement to keep things simple for a viva.
2. `MOCK_MODE` defaults to `true` so the project is fully runnable and
   demonstrable without requiring anyone to obtain an API key.
3. Trunk mismatch, missing DHCP pool, incorrect DHCP network, ACL
   blocking, NAT missing, and NAT translation absent were all implemented
   as "useful if practical" additional checks, per the brief's suggestion.
4. The five deliberately-wrong AI mock diagnoses were chosen to match the
   five example mistake patterns given in the audit brief (routing vs.
   ACL, DHCP outage vs. exhaustion, VLAN vs. trunk, DNS vs. gateway, NAT
   vs. NAT-blocking ACL) exactly.
5. "Dashboard showing issue types, severity, and AI-vs-human agreement" was
   interpreted as the 5-tab Streamlit layout described above, since the
   brief allowed Streamlit as the default beginner-friendly choice.
6. The exact target category distribution (VLAN 5 / Gateway 4 / DHCP 5 /
   DNS 4 / Routing 5 / ACL 4 / NAT 4 / Wireless 4) was achieved exactly by
   rewriting one existing case's content rather than deleting it, per the
   audit brief's "do not delete useful existing cases unnecessarily"
   instruction.
