# NetSage AI — Architecture

## 1. High-level pipeline

```
INPUT (symptom + topology note + show-command evidence)
        |
        v
Case selection (case_loader.py)
        |
        v
Rule-based validation (rule_checker.py)   <-- deterministic, no AI
        |
        v
AI diagnosis (ai_diagnoser.py)            <-- mock or live LLM, isolated
        |
        v
Evidence comparison (main.py)             <-- AI's answer vs. rule findings
        |
        v
Human review (human_review.py)            <-- Accept / Edit / Reject, mandatory
        |
        v
Final diagnosis                           <-- reviewer decision wins, always
        |
        v
Dashboard / logging (dashboard.py, outputs/review_log.json)
```

## 2. Why two separate diagnosis paths?

The brief explicitly requires that **"The deterministic checker should NOT
be replaced by the AI."** These are two independent, complementary tools:

- `rule_checker.py` parses the raw text of `show_outputs` with regular
  expressions. It is 100% reproducible — the same input always produces the
  same output — and needs no API key or network access. It is good at
  catching structural configuration problems (a shutdown interface, an IP
  address in the wrong subnet, a missing VLAN) but cannot reason about
  behavioural or application-layer symptoms (DNS server choice, wireless
  interference, DHCP pool exhaustion vs. outage).

- `ai_diagnoser.py` reasons over the same evidence in natural language,
  citing specific lines, and can handle the softer cases the rule checker
  cannot. It is explicitly instructed (see `prompts/diagnose_prompt.md`)
  to never claim certainty when evidence is thin, and to always flag
  `needs_human_review = true`.

In the dataset, roughly half of the 35 cases trigger at least one
deterministic rule-checker finding; the AI is used for all 35, and the
rule-checker findings (when present) are passed to it as extra corroborating
context. This split is intentional and is called out explicitly in the demo
script and viva answers — it is not a gap in the implementation.

## 3. Module responsibilities

| Module              | Responsibility                                                   |
|---------------------|---------------------------------------------------------------------|
| `src/utils.py`         | Shared helpers: JSON I/O, timestamping, safe JSON parsing         |
| `src/case_loader.py`   | Loads/filters the case dataset                                    |
| `src/rule_checker.py`  | 12 deterministic checks over show-command evidence                |
| `src/ai_diagnoser.py`  | Isolated AI integration (mock + live LLM), single `diagnose()` API |
| `src/human_review.py`  | Records and reports Accept/Edit/Reject decisions                  |
| `src/main.py`          | CLI pipeline / interactive demo / batch runner                    |
| `src/dashboard.py`     | Streamlit dashboard (metrics, issue analysis, case detail)        |

## 4. Data flow and storage

- `data/sample_cases.json` / `data/cases.csv` — the 35-case dataset (same
  data, two formats; JSON is the canonical source, generated by
  `tools_generate_data.py`).
- `data/responsible_ai_log.csv` — 5 curated, documented examples of the AI
  being wrong and a human correcting it (see `docs/responsible_ai.md`).
- `outputs/review_log.json` — created at runtime by `human_review.py`;
  every Accept/Edit/Reject decision made through `main.py` or the dashboard.
- `outputs/sample_diagnoses.json` — produced by `python3 src/main.py --batch`;
  a full run of the pipeline across all 35 cases in mock mode.

## 5. Why this design is "safe by construction"

1. `ai_diagnoser.diagnose()` hard-codes `needs_human_review = True` on every
   return path — even a live LLM response that forgets to set it is
   overridden.
2. `human_review.save_review()` refuses to store an EDIT/REJECT decision
   without a `corrected_diagnosis`, forcing reviewers to actually engage.
3. No module in this codebase ever writes to a device or applies a
   configuration change. `fix_steps` are always described as
   recommendations for a human to carry out and verify.

## 6. Audit changelog (post-submission hardening pass)

A full requirement audit against the original brief found and fixed the
following real issues (not just documentation touch-ups):

1. **Category miscounting bug.** `case_loader.filter_cases()` originally
   matched a category keyword as a loose substring against each case's
   symptom/concept/expected_fault text. Because a case's *symptom
   description* often mentions another category's term (e.g. a gateway
   case whose symptom says "VLAN 20 lost access..."), this double-counted
   cases and fed inflated numbers into the dashboard's Issue Analysis tab.
   Every case now carries a single, explicit `category` field assigned at
   dataset-generation time, and `filter_cases`/`dataset_summary` match
   against it exactly — counts now always sum to the total case count.
2. **Dataset rebalanced.** VLAN dropped from 6 to 5 cases; `CASE-006` was
   rewritten from a VLAN case into a distinct NAT case (a static NAT entry
   pointing at a server's stale internal IP after a rebuild), bringing NAT
   from 3 to 4. Final distribution: VLAN 5, Gateway 4, DHCP 5, DNS 4,
   Routing 5, ACL 4, NAT 4, Wireless 4 = 35.
3. **`acl_blocking` false-WARN fixed.** The "ACL has permits but no
   trailing `permit ip any any`" heuristic was firing on standard/NAT-source
   ACLs, which legitimately never use that syntax. It is now scoped to only
   apply when the evidence actually shows an *Extended* ACL.
4. **`gateway_mismatch` false-positive risk fixed.** The original check
   compared a client's gateway IP against IPs found via a literal `"ip
   address"` text match, which never matched `show ip interface brief`
   tabular output — meaning every gateway would have been flagged
   regardless of correctness. It now requires router/switch interface
   evidence to actually be present before judging a mismatch, and confirms
   a match by occurrence count rather than a brittle substring list.
5. **Live-mode error handling hardened.** `ai_diagnoser.diagnose()` now
   catches missing API key, Anthropic API errors, malformed/unparseable
   JSON, and network/timeout failures, returning a clearly-labelled
   fallback diagnosis (`_source: "error_fallback"`) instead of raising an
   unhandled exception.
6. **CLI review-input hardening.** `main.py`'s interactive Accept/Edit/
   Reject prompt now validates the decision (re-prompts up to 3 times on
   invalid input) and requires a non-empty corrected diagnosis for
   EDIT/REJECT, instead of crashing with a raw traceback on bad input or
   EOF.
7. **Test suite expanded** from 20 to 42 tests, adding coverage the audit
   found missing: `wrong_subnet_mask`, `missing_route`, `trunk_mismatch`,
   and `acl_blocking` (positive *and* negative cases, including a
   regression test for finding #3 above), plus a new `test_ai_diagnoser.py`
   covering mock response schema/range validity and Responsible AI log
   data integrity.
